Quartz 网站优化路线图

这份清单的定位变了：发布正确性和站点基础已经打完，现在剩下的是内容组织、图片流程和长期可维护性。原则仍然是一次只推进一件，不做大重构。

一、已经完成（不要再重复规划）

站点基础

  • baseUrl 改成自定义域名，locale 改成 zh-CN
  • 构建产物生成 CNAME，自定义域名稳定生效
  • 页脚换成站内导航入口
  • 部署改用 npm ci（老流程遗留项，已无影响）

内容结构

  • 首页改成七分类门户（index.md 的 portal-card 布局）
  • 各分类入口页做成目录页：道、霸天玩易、人生感悟、技术总结、素食科技、我的计划、过去的事
  • 全库重组：01-道、02-霸天玩易、素食科技独立
  • frontmatter 五字段统一（title / description / date / tags / status）

发布自动化

  • 内容源改为坚果云同步（全平台）
  • 服务器每 5 分钟检测 + 钩子构建 + 推 gh-pages，GitHub Pages 自动发布
  • 失败邮件告警、锁、重试、日志轮转
  • 手机端彻底退出运维（不用 Termux / git / SSH）

图片

  • 415 张易学插图 + 总架构图迁到 Cloudflare R2（img.longbatian.site）
  • 本地图片副本删除，Z-附件 清空
  • 章节图片统一用 <img width=...> + 图注写法，支持灯箱放大

二、待做（按优先级）

P1：图片流程要顺手

  • 把 R2 上传固化成一个可复制的命令（含参数、密钥来源）
  • 桌面端接自动上传插件：粘图即传、自动替换直链
  • 统一图片命名规则（现在 415 张全是 8 位随机串，看不出内容）
  • 建图片清单：哪张图属于哪一章，便于清理与迁移

P2：首页与导航自动化

  • 首页「最近更新」现在手写，考虑改成自动取的「最近发布」组件
  • 分类入口页的文章数、精选链接也是手写，容易和实际数量脱节（例如「152 篇正文」需要人工校准）
  • 标签页整理：合并同义标签，删掉只用过一次的孤立标签

P3：写作体验

  • 统一「草稿 → 正式」的状态约定（status 字段的实际用法）
  • 给常用文章类型做 frontmatter 模板（技术总结 / 易学章节 / 菜谱 / 故事）
  • 站内搜索的关键词覆盖检查：重要概念能不能搜到

P4：性能与成本

  • 评估关闭自定义 OG 图片生成，缩短构建时间
  • 看是否需要本地字体方案（现在依赖外部字体加载）
  • gh-pages 历史体积清理（每次全量构建都会新增提交）
  • 检查 R2 图片是否有超大文件，批量压缩

三、已作废的条目

这些是旧方案下的计划，现状已经不需要：

  • deploy.yml 里保留 keep_files: true —— 构建已迁到服务器，Actions 不再是发布主路径
  • GitHub Actions 里做 npm ci + build —— 同上，服务器负责构建
  • 本地写脚本 git 同步 content/ —— 已由坚果云同步取代
  • 在手机端配置 SSH / Termux —— 已废弃
  • 「图片归档到固定目录」 —— 被 R2 图床方案取代：图片不再进库

四、长期：服务器退役预案（2027-09-12 前的作业）

  • 服务器到期前确认：坚果云内容完整、线上站点是最新版本
  • 决定后续路线：本地手动构建发布 / 迁到另一台机器 / 换 GitHub Actions + 坚果云方案
  • 撤销 rclone 应用密码、GitHub deploy key、SMTP 授权码
  • 保留一份「没有服务器也能发布」的操作说明（目前还没有）

执行顺序建议

  1. 先把图片流程做顺（P1）—— 因为它是唯一还需要电脑手动介入的环节。
  2. 再处理首页与分类页的手写数字（P2）—— 影响观感和准确性。
  3. P3、P4 有空再做，不急。
  4. 退役预案提前一年开始想，别拖到最后一个月。

备注

站点内容本身就是公开展示用途，不需要做隐私隔离。真正的风险只有两个：误删内容 和 服务器到期后没有替代方案，其余都是体验优化。
